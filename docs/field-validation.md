# Field validation

## Black-box smoke test

`npm run test:smoke` (runs `tests/smoke.sh`, curl as an attacker against `BASE`, default http://localhost:8888).

Prerequisite: pretty permalinks. wp-env defaults to plain permalinks, where Apache 404s `/robots.txt`, `/db-backup/` and `/.env.bak` before WordPress sees them. Run once:

    npx wp-env run cli wp rewrite structure '/%postname%/' --hard

Observed (wp-env, WP 6.5, default settings, p=0.7): `SMOKE OK`, 30/50, 31/50, 33/50 and 33/50 REST users responses suppressed after the trap hit. Expected about 35; the script requires at least 20.

## Cache compatibility (WP Super Cache)

- Latest WP Super Cache needs WP 6.8; wp-env runs WP 6.5, so it will not install. Version 1.9.4 installed from the wordpress.org zip URL and activated:
  `npx wp-env run cli wp plugin install https://downloads.wordpress.org/plugin/wp-super-cache.1.9.4.zip --activate`
- The plugin has no WP-CLI command in this version. Caching was enabled by setting `$cache_enabled = true;` in `wp-content/wp-cache-config.php` (the plugin had already set `WP_CACHE`). Mode was the default PHP caching.
- Results:
  - Homepage is cached ("Cached page generated by WP-Super-Cache" footer, `Cache-Control: max-age=3, must-revalidate` on hits). The cached file still contains the hidden `display:none` honeypot link and the HTML comment notices.
  - `/db-backup/` returns 200 with `Cache-Control: no-store` on repeated requests, and no cache file was written for it.
  - `/wp-json/wp/v2/users` is not cached (`Cache-Control: no-store`) and the suppression ratio was unchanged (33/50).
  - `tests/smoke.sh` passed with caching enabled.
- Caveat (not exercised): in PHP-cache mode a cached page is served before plugins load, so a flagged IP requesting an already-cached page gets the normal cached page plus static layer, not a dynamic response. Dynamic behaviors (traps, REST suppression) are on uncached paths. Mod_rewrite "Expert" mode was not tested.
- WP Super Cache was deactivated afterwards to leave the dev site clean.
